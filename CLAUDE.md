# CLAUDE.md

## Project Overview

Workbench is a Tauri v2 + Svelte 5 desktop terminal manager. Users add local project folders, and each project gets a tabbed workspace with real shell terminals (via `portable-pty` + `xterm.js`). Config persisted to `~/.workbench/projects.json`, workspaces to `~/.workbench/workspaces.json`.

It is a **monorepo** (Cargo workspace + bun/Turborepo workspace). Beyond the desktop app it ships a **headless control-plane server** (`workbench-server`) that can run on any machine — and the desktop app can host the same server in "server mode". The server lets another device (phone/desktop) list/create worktrees and run terminals and Claude/Codex chats on its machine (HTTP control plane + terminal/chat WebSockets).

### Monorepo layout

```
Cargo.toml / package.json / turbo.json   # workspace roots (repo root)
apps/
  desktop/      # the Tauri app: src/ (Svelte frontend) + src-tauri/ (Rust, crate `workbench`)
  server/       # workbench-server: headless axum control plane (lib + bin), NO tauri
  mobile/       # Tauri Android client: chat-first home, chat + terminal views (see docs/MOBILE.md)
crates/
  workbench-core/   # shared pure Rust logic (no tauri): config, git, sessions, settings, types
packages/
  types/             # @workbench/types: shared TS types (mirror of workbench-core serde types)
  transport/         # @workbench/transport: ControlPlaneTransport (Tauri/Http/mock impls), typed via @workbench/types
  ui/                # @workbench/ui: shadcn-svelte primitives + cn(); subpath exports (@workbench/ui/button …)
  theme/             # @workbench/theme: theme.css — design tokens, accent presets, Tailwind v4 @theme mappings
  control-plane-ui/  # @workbench/control-plane-ui: transport-driven ControlPlaneStore + ControlPlaneSidebar (desktop-remote)
  chat-ui/           # @workbench/chat-ui: Claude chat view (AgentChat, agentClient, ChatTranscript, composer, cards) for desktop + mobile
plugins/workbench/    # Claude Code plugin (mod) reporting session activity to the hook bridge; injected only (no marketplace), so `plugin.json` is all it keeps of `.claude-plugin/`. Workspace package @workbench/claude-plugin: `test` = bun test (`test/`, the link's timeouts and retries against a fake fetch), `check` = tsc against types/claude-code.d.ts (the plugin API Claude Code 2.1.291 writes; replace it whole when bumping the tested CLI), `lint` = eslint; `claude plugin validate plugins/workbench` locally (no CLI in CI)
docs/                # SIGNING, SANDBOX_RUNTIME, MOBILE, LANDING_PAGE deep dives
.design-sync/        # claude.ai/design sync inputs (tokens-only; see its NOTES.md)
```

`@workbench/ui` owns the shadcn primitives (`@workbench/ui/<component>`) and `cn`/type-helpers (`@workbench/ui` root). `@workbench/theme` (`packages/theme/theme.css`) holds every token, the accent presets, the `@theme inline` utility mappings, the base layer and the `@source` lines that make Tailwind v4 scan `packages/ui`, `packages/control-plane-ui` and `packages/chat-ui`; each app's `app.css` imports it after `tailwindcss`. `@workbench/control-plane-ui` is a clean, transport-driven shared sidebar (list projects, view/create worktrees and their GitHub links, no terminal IO) — consumed by the desktop's **remote-client mode** (ActivityRail "Remote server" → `RemoteServerDialog`, `HttpTransport`). The mobile app uses its `ControlPlaneStore` but has its own home screen. `@workbench/chat-ui` holds everything platform-neutral about the chat view; hosts call `setChatPlatform` for what differs (link opening: desktop the `open_url` command, mobile `plugin-opener`; OS file drops: desktop only) and pass an `AgentApi` (`agentClient(() => ({ baseUrl, token }))`).

Not yet extracted (deferred; desktop keeps its own terminal-coupled `ProjectSidebar`/stores): splitting the desktop `ClaudeSessions`/`Workspace` stores into shared core slices. The desktop's rich sidebar is intentionally NOT shared — it's coupled to terminals/git/github; the shared `ControlPlaneSidebar` is the lean cross-platform one.

Three Cargo crates: `workbench` (desktop, depends on core + server), `workbench-core` (pure logic), `workbench-server` (lib+bin). `workbench-core` and `workbench-server` must **never** depend on `tauri` — verify with `cargo tree -p workbench-server | grep -i tauri` (must be empty). Tauri deps live only in `apps/desktop/src-tauri/Cargo.toml`.

## Release

- **GitHub releases:** created automatically by GitHub Actions (`tauri-action`) when a `v*` tag is pushed. **Do not** run `gh release create` manually — it causes duplicate/empty releases.
- **Issue/PR linking:** enabled — append `(#N)` references to changelog entries so GitHub auto-links them.
- **Tag format:** `v`-prefixed semver (e.g. `v0.18.0`).
- **Changelog location:** `changelog/RELEASE_{version}.md`.
- **Release flow:** write changelog → commit → tag → push commit + tag → let CI publish the release.
- **Android APK:** the `android` job in `release.yml` (ubuntu, NDK r29, `aarch64` only) builds `apps/mobile` in parallel with desktop, signs it from the `ANDROID_*` secrets (hard failure when empty; see `docs/SIGNING.md` §Android) and uploads `workbench-android-<version>.apk` + `.sha256` as an artifact; `publish` attaches them to the draft (which `build`'s tauri-action creates, so no race) before un-drafting. `workflow_dispatch` runs only the Android build (artifact, no release). Mobile `tauri.conf.json` `version` is synced from the tag like desktop; Tauri derives `versionCode = major*1_000_000 + minor*1_000 + patch`. Release builds allow cleartext (the server is plain HTTP/WS).
- **Windows signing:** Azure Artifact Signing via the `starkey-digital` org's `AZURE_*` secrets; `signCommand` is in `apps/desktop/src-tauri/tauri.windows-sign.json`, merged with `--config` only by the release job, and the job verifies both signatures (`docs/SIGNING.md` §Windows).
- **macOS signing/notarization:** see `docs/SIGNING.md`. Driven by `APPLE_*` GitHub secrets; the release workflow fails when any is empty, unless the repo variable `ALLOW_UNSIGNED_RELEASE=true`. Local signed builds: `bun run --cwd apps/desktop build:signed` + a `signing.env` at the repo root.

## Workflow

**Default flow for all non-trivial work** — never commit directly to `main`:

1. **Branch:** create a feature branch off `main` (e.g. `feat/...`, `fix/...`). `main` has force-push protection.
2. **Commit:** Conventional Commits format. Commit/push only when the change is complete or the user asks.
3. **PR:** open a PR with `gh pr create`. Reference issues/PRs with `(#N)` so GitHub auto-links.
4. **Auto-merge:** add the `automerge` label (`gh pr create --label automerge`, or `gh pr edit N --add-label automerge`) — don't sit and babysit checks unless asked. **Kodiak** (GitHub App, `.kodiak.toml`) acts as the merge queue: it keeps labelled PRs up to date with `main` (branch protection requires up-to-date branches, so without it every merge to `main` strands the other PRs as BEHIND) and squash-merges once `frontend`/`rust`/`rust-windows`/`rust-macos`/`e2e` pass. It keys off the label (`require_automerge_label`), not GitHub's native `gh pr merge --auto`. Titles matching `WIP`/`DRAFT`/`DO NOT MERGE` or labels `wip`/`do-not-merge` block it. GitHub's built-in merge queue isn't available — it's org-only and this repo is user-owned.
5. **Cleanup:** Kodiak deletes the branch after merge (`delete_branch_on_merge`).

The `github-pr` / `prep-pr` skills automate this; prefer them over hand-running `gh`.

**CI scope** (`.github/workflows/ci.yml`): a `changes` job (`dorny/paths-filter`) decides what a diff needs. Docs-only changes (`**/*.md`, `docs/`, `changelog/`, `site/`, `.design-sync/`) run only the prettier check; Rust suites run only when Rust inputs change (`*.rs`, `Cargo.*`, `crates/`, `apps/server/`, `apps/*/src-tauri/`, `ci.yml`). The required checks (`frontend`/`rust`/`rust-windows`/`rust-macos`/`e2e`) always report: gate them with job- or step-level `if:`, never workflow-level `paths`/`paths-ignore`, or a filtered-out required check blocks the PR forever. If `changes` fails, every suite runs. Rust jobs run from the repo root (`cargo test --workspace`, which also runs `workbench-core`, `workbench-server` and `apps/server/tests`). `e2e` installs WebKit deps with plain `apt-get` (`cache-apt-pkgs-action`'s `.debs` from an older runner image mixed Mesa versions and broke WebKit). Leave `swatinem/rust-cache` on its default `target/`: the Cargo workspace is the repo root, so pointing `workspaces:` at a member dir caches nothing.

## Commands

Run from the repo root. JS tasks go through Turborepo (the local `turbo` binary — invoke via `bun run`, not a global `turbo`).

- **Install:** `bun install` (bun workspaces link `@workbench/*` into the consuming app's `node_modules`)
- **Dev:** `bun run dev` (`turbo run dev --filter=@workbench/desktop` → `tauri dev`, Vite on 1420). `tauri dev` is its own instance: config in `~/.workbench-dev` (`tauri::is_dev()` → `paths::set_workbench_config_dir`, not inherited by its shells; the first run copies `projects.json`), so it runs beside the installed app without touching its settings or plugin copy
- **Build:** `bun run build` (`turbo run build`)
- **Typecheck:** `bun run check` (`turbo run check` — svelte-check on desktop, tsc on packages)
- **Lint:** `bun run lint` (root `prettier --check .` then `turbo run lint` — eslint per package)
- **Format:** `bun run format` (`prettier --write .`)
- **Rust:** `cargo build` / `cargo test` / `cargo clippy` operate on the whole workspace; scope with `-p workbench|workbench-core|workbench-server`.
- **Android (mobile):** `cd apps/mobile && bun run tauri android build --apk --target aarch64` (`--debug` for debug; `bun --cwd apps/mobile run tauri …` does not work). Needs `ANDROID_HOME`, `NDK_HOME`, `JAVA_HOME` (JDK 21). Launcher icons: `bunx tauri icon app-icon/manifest.json` from `apps/mobile` (adaptive foreground/background SVGs live in `app-icon/`).
- **Server (standalone):** `cargo run -p workbench-server -- --port 4317 --token <32+ chars>` (flags: `--bind`, `--port`, `--token`, `--insecure-no-token`; envs `WORKBENCH_BIND/PORT/TOKEN`). Refuses to start on a non-loopback bind without a token unless `--insecure-no-token`; a token shorter than 32 chars is always refused.

### Tests

Maps onto Tauri v2's three testing layers (https://v2.tauri.app/develop/tests/): **(1)** mock the frontend IPC boundary, **(2)** test Rust `#[tauri::command]`s under the mock runtime, **(3)** WebDriver e2e for the GUI.

- **Layer 1 — frontend IPC.** Control-plane code depends on the `ControlPlaneTransport` abstraction, so tests **inject `createMockTransport()`** (dependency inversion — preferred over monkey-patching `mockIPC`). Direct `@tauri-apps/api` paths (native terminal IO, events) are intercepted by `apps/desktop/src/test/tauri-mocks.ts` (`vi.mock('@tauri-apps/api/{core,event}')` exposing `listenSpy` / `emitMockEvent` / `clearListeners`) — our hand-rolled equivalent of `@tauri-apps/api/mocks`.
- **Layer 2 — Rust commands via the mock runtime.** `tauri::test` (`mock_builder().manage(state).build(mock_context(noop_assets()))`) drives `#[tauri::command]`s with no webview. Enabled by `tauri = { features = ["test"] }` declared as a **dev-dependency** (`apps/desktop/src-tauri/Cargo.toml`) so feature unification keeps `test` out of release builds. Example: `server_control.rs`'s `lan_start_status_stop_cycle` exercises the start/stop/status commands (a repeat start with the same token is a no-op; a different token restarts); `rotating_the_token_restarts_a_running_lan_listener` asserts the old token is rejected after rotation; `listeners_share_terminals_across_lan_restarts` proves both listeners see one terminal set. Thin wrapper commands (`commands.rs` etc.) stay untested at this layer — their logic lives in `workbench-core` (unit-tested).
- **Layer 3 — WebDriver e2e: smoke only** (`apps/desktop/e2e`). WebdriverIO's `@wdio/tauri-service` with the **embedded** provider: `tauri-plugin-wdio-webdriver` runs a W3C WebDriver server inside the app, so it works on macOS (WKWebView), where `tauri-driver` doesn't. The plugin is behind the opt-in cargo feature `e2e` and a `compile_error!` blocks it in release: it's an unauthenticated server on `127.0.0.1:4445`, and sandboxed sessions can reach loopback, so it must never be in `tauri dev` or shipped builds. `bun run --cwd apps/desktop build:e2e` (`tauri build --debug --no-bundle --features e2e`) then `test:e2e`. `wdio.conf.ts` points `WORKBENCH_CONFIG_DIR` at a temp dir seeded with the repo as the only project. Specs check boot, sidebar, the Scripts tab and the settings window; the `e2e` CI job (Ubuntu + xvfb) is a required check. `tauri-plugin-wdio` (mocking/log capture) is not installed: its `execute` permission runs arbitrary JS.
- **Rust (`cargo test`):** `workbench-core` units, the `workbench` desktop crate units (dispatchers, `server_control` mock-runtime), `workbench-server` units, and `apps/server/tests/server.rs` (e2e: real server on an ephemeral port, driven with reqwest + a `tokio-tungstenite` WS client). The e2e suite covers the cwd allowlist (`/agent/files`, terminal create rejecting an unknown worktree), server-built Claude commands, the terminal cap, bearer auth (no/wrong token → 401 on HTTP and WS, weak token refused), foreign-`Origin` WS rejection (403), two listeners sharing `Managers`, and WS-close on kill **and** on shell exit. Every embedded test server needs a ≥32-char token (`TOKEN` const + `client()` / `ws_url()` helpers).
- **Test env knobs** (read by the server/core at runtime): `WORKBENCH_CLAUDE_BIN` (fake `claude`; also what a chat's terminal runs, so chat tests point it at `tests/support`'s Python plugin bridge, which runs the stream-json stand-in named by `WORKBENCH_FAKE_CLAUDE` and talks `/mod/*` for it), `WORKBENCH_CONFIG_DIR` (isolate `~/.workbench`; write a `projects.json` so the **cwd allowlist** accepts the test dir — see `register_project()`), `WORKBENCH_MAX_TERMINALS` (low cap for the cap test). These mutate **process-global** env, so env-mutating tests hold the module `ENV_LOCK` mutex (`env_guard()`) and only one test may depend on a given value at a time.
- **JS (`turbo run test`):** `@workbench/transport` (HTTP route mapping, undefined-param dropping, error handling, `MockTransport`, `/events` reconnect backoff, `terminalWsUrl`, **and the `TauriTransport` shim** — `tauri.test.ts` mocks `@tauri-apps/api/{core,event}` to assert the omit-args-when-undefined call shape + listener wiring), `@workbench/control-plane-ui` (`ControlPlaneStore` via `createMockTransport`), `@workbench/desktop` (stores/utils via injected `createMockTransport`; `InstancesStore`/`RemoteInstance`), `@workbench/chat-ui` (`AgentChat` with a fake socket, chat formatting, image intake), and **`@workbench/mobile`** (jsdom vitest: `MobileClient` in `client.svelte.ts` — extracted from `App.svelte` so the connection/terminal/chat logic is unit-testable — terminal reconnect status, home-screen labels, and the home stream with a fake `EventSource` in `home-stream.test.ts`). The phone's Home follows `GET /events/home` (`home-stream.ts` `HomeStream`, opened by `MobileClient.watch()` only on Home with the app in front, closed otherwise; backoff 2s→60s, a stream silent 45s counts as dead); while it isn't live (connecting, failed, or a host without the route) the 4s poll runs, one round at a time with a 10s timeout on the terminal list. Mobile component rendering (xterm) is intentionally not tested; the logic lives in the store/helper.
- **Cross-language integration** (`packages/transport/src/http.integration.test.ts`): drives the real `HttpTransport` against the real `workbench-server` binary (`list_projects` round-trip, `git_status` rejecting an unknown worktree; registers its project dir via `WORKBENCH_CONFIG_DIR`). Auto-**skips** unless `target/debug/workbench-server` exists, so build it first (`cargo build -p workbench-server`); otherwise `turbo test` silently skips it.
- **Deliberately not unit-tested — this is the WebDriver layer's job:** rendered `.svelte` component interaction. Our components are thin context-coupled views that delegate to the thoroughly-tested stores, and they wrap Bits UI / shadcn primitives (dialog portals, focus traps) that are friction-prone and flaky under jsdom. So the policy is: **push real logic out of components into stores/helpers and unit-test that** (e.g. `MobileClient`, `terminalWsUrl`), rather than render-test the views. Rendering is smoke-checked by the WebDriver layer; keep new component behaviour in stores/helpers anyway.
- Also not covered: the `terminal.rs` attach lock-ordering reattach race (timing-only) and the `spawn_blocking` offloading (behavior-preserving — no observable change to assert).

Use **Bun** exclusively — do not introduce npm/yarn/pnpm lockfiles. Prettier runs at the root (single pass, keeps prettier-before-eslint ordering); eslint runs per package via turbo.

## Architecture

### Tauri v2 model

- **Rust backend** (`apps/desktop/src-tauri/src/`): Window management, native macOS terminals, Tauri commands, embedded server control. Crate `workbench` (lib name `workbench_lib`).
- **Frontend** (`apps/desktop/src/`): Plain Svelte 5 + Vite (no SvelteKit). Dev: `http://localhost:1420`; prod: `apps/desktop/dist/index.html` (tauri `frontendDist` is `../dist` relative to `src-tauri/`).

### Shared core crate (`crates/workbench-core/src/`)

Pure, non-Tauri logic reused by desktop and server. All `Serialize`/`Deserialize`, all return `anyhow::Result`:

- `types.rs` — Shared serde types (`ProjectConfig`, `CreateWorktreeRequest`, `WorkbenchSettings`, workspace snapshots, GitHub/Trello types). The single wire contract for both Tauri IPC and the server's JSON API (`#[serde(rename_all = "camelCase")]`).
- `config.rs` — Project/workspace/settings persistence (`~/.workbench/`)
- `git.rs` — Git CLI wrappers: branch info, worktree CRUD, branch listing
- `worktrees.rs` — the one worktree create/remove behind both the Tauri commands and `POST`/`DELETE /projects/worktrees`: the repo must pass the cwd allowlist, and a create fills an unset strategy/start point/fetch from the host's settings and always computes the path from the layout (`CreateWorktreeRequest` has no `path`; an older client's is ignored), so clients send only the branch and per-call picks (copy options); remove checks registration and lists worktrees once, deletes the branch on `deleteBranch` and answers `{branchDeleted}` (a client seeing no such field, an older host, deletes the branch itself).
- `cwd.rs` — `resolve_cwd`, the cwd allowlist (a registered project or a known worktree of one) for terminal creates, chat starts, `/agent/files`, git review and worktree changes; a refusal is `cwd::NotAllowed`, which the server's `ApiError` answers with 403. The server re-exports it as `crate::cwd`.
- `claude_sessions.rs` / `codex_sessions.rs` / `codex_config.rs` — session discovery (`~/.claude/`, `~/.codex/`)
- `claude_launch.rs` — builds every Claude terminal command (server terminals, native `create_native_terminal`), so no client can skip the sandbox or permission mode: `startup_command(command, claudeSession)` (not both) → `terminal_command` (`--resume`/`--session-id`, permission mode, srt wrapper failing closed without its settings file, a new session's `prompt` after `--`; Windows drops an unsafe prompt, `prompt_notice` says why). Holds the `SANDBOX_RUNTIME_PACKAGE` pin and trust-dialog helpers.
- `claude_transcript.rs` (+ `claude_transcript/`) — folds Claude session JSONL (history) and the stream-json lines the Workbench plugin translates a terminal `claude` into chat items: streamed text fills an item the final block replaces in place, tool results update their call, `can_use_tool` becomes an approval answered via `resolve_approval`, `control_cancel_request` expires an approval, and so does its call's tool result or the turn's `result` unless a background agent task still runs (an asking hook that died leaves no card answerable for nobody; `ModLink::keep_asks` drops those asks too). Claude MCP elicitations are answered only in the terminal: the plugin's `workbench_terminal_elicitation`/`_result` lines make a read-only `inTerminal` `Elicitation` item, cleared by its result or at turn end. `claude_transcript/elicitation.rs` (filters accepted content to the schema) serves Codex's `mcpServer/elicitation/request`. History follows the JSONL's `parentUuid` tree (`branch.rs`): a rewind leaves the old tail in the file as a dead branch, and `load`/`load_at(leaf)` show only the live one, as the CLI does. `protocol.rs` inventories, as handled or ignored, the SDK `SDKMessage` kinds (0.3.286 ↔ CLI 2.1.286) the plugin sends, the plugin's own, and the JSONL kinds; unknown kinds are logged once. `events.rs` folds side events into `Event` items (denied tools incl. `system:permission_denied`, hooks that failed/blocked/spoke from JSONL `hook_*` attachments + `stop_hook_summary` — never a line per successful hook — recalled memories, model refusals), `Artifact` results with a `url` into `meta.artifacts` (the link only exists in the structured result), and `prompt_suggestion` into `meta.promptSuggestion`, cleared when a turn starts. `goal.rs` folds `/goal`'s JSONL `goal_status` attachments into `meta.goal` (set: `met:false`+`sentinel`; a failed check: `met:false`+`reason`; achieved: `met:true`, plus a "Goal achieved" notice; cleared: `met:true`+`sentinel`); `/clear` ends it, `/resume` takes the resumed JSONL's. The plugin sees the attachment without its fields, so it sends `workbench_goal_status {uuid}` and the server folds the newest `goal_status` row in the JSONL tail once that one is written (`goal_status_entry`, retried briefly; `AgentSession::learn_goal_status`), and again at each `result` while a goal shows. Goal turns chain inside one turn (the goal's Stop hook blocks), so busy and the `result` need nothing special. Chat: `ChatGoal` above the composer (condition + the latest "not met yet" reason, live chats only).
- `codex_transcript.rs` (+ `codex_transcript/`) — folds `codex app-server` JSON-RPC notifications and server requests into the same `TranscriptItem`/`TranscriptMeta` (a command is `Bash`, a file change `Write`/`Edit` with hunks, the plan `TodoWrite`, a question `AskUserQuestion`, an MCP elicitation the same `Elicitation` item as Claude's), so one chat view renders both CLIs. Approvals answer the JSON-RPC request; Always allow is offered only when codex offers `acceptForSession` (never the execpolicy amendment — that saves a lasting rule); deny is `decline`, else `cancel` (ends the turn). Unservable requests get an immediate error/decline (unanswered, codex waits forever). `fixtures/app-server-0.159.3.jsonl` is a recorded real turn; regenerate shapes with `codex app-server generate-ts --experimental`; see `docs/CODEX_IMPLEMENTATION.md`.
- `settings.rs` — Claude Code settings CRUD, plugin/skill/hook discovery
- `github.rs` — GitHub CLI wrappers
- `package_scripts.rs` — root `package.json` reader for the Scripts tab: package manager from `packageManager`, then lockfile, then npm; scripts in file order (custom visitor, since `serde_json` maps sort); script names with shell-special characters are dropped because they're typed into a shell as `<pm> run <name>`
- `trello/` + `trello_automation.rs` — Trello API integration (async; uses a self-built Tokio runtime, no Tauri)
- `chat_attachment.rs` (a dropped chat file → image / PDF / text attachment; limits shared with the server), `project_files.rs` (the `@` mention file list)
- `claude_plugin.rs` — embeds `plugins/workbench` (`register.ts` → `chat.ts`, every hook and `$` call → `link.ts` (server link, outbox, asks; every request bounded on `Date.now()` deadlines checked by the 50ms timer, each queued line and each settled request, asks and hellos also by a `$.clock.after`) + `lines.ts` (line builders) + `asks.ts` (pending `tool.check` asks, FIFO per tool+input), no engine calls; one hooks module per plugin, and `$` may only be spelled `$.noun.method(...)` inside a hook, never stored or passed) and writes it to `~/.workbench/claude-plugin/workbench`; `plugin_dirs_env()` is the `CLAUDE_CODE_PLUGIN_DIRS` every shell/chat process gets next to `WORKBENCH_HOOK_SOCKET`: our copy first, any other `*/claude-plugin/workbench` dropped. A Workbench started from another's terminal inherits that one's wiring, so desktop `run()` and the standalone `main` call `shell::scrub_inherited_env()` first thing (removes `shell::PARENT_ONLY_ENV` — `WORKBENCH_{MOD_URL,MOD_TOKEN,HOOK_SOCKET,PANE_ID,PERMISSION_MODE}` — and the inherited plugin copy), and server terminals, Codex chat processes and the `claude` probes `env_remove` those vars before setting their own. Replaced the old `workbench-hook-bridge` settings.json script for Claude (the desktop removes it at startup, `settings::remove_workbench_hook_integration`); Codex keeps its `notify` script. The plugin forwards `classic.*` hook events as an HTTP POST to the server's bridge (`apps/server/src/hook_bridge.rs` + `http.rs`, `application/json` only; the server stamps `WORKBENCH_HOOK_SOCKET` on every terminal and chat itself, so no client sends `hookSocket`, and mirrors a Codex TUI's finished turn into the attention feed), awaited for order but raced against a 3s `$.clock.sleep` (a hung bridge is then skipped 30s); `WORKBENCH_HOOK_SOCKET` is `host:port#secret`, a per-launch secret the bridge checks constant-time (`x-workbench-hook-secret` header; a `secret` field in Codex's notify-script lines; `HookBridgeState::address()` is the bare `host:port` for srt's allowlist). The repo is no longer a marketplace: `claude_plugin::disable_marketplace_install_at_startup` (desktop `run()` and the standalone server `main`, in a background thread; `spawn_disable_marketplace_install` also runs for accounts `save_workbench_settings` adds) reads each account's `plugins/known_marketplaces.json` read-only and, only when its `workbench` entry's source is exactly datstarkey/workbench or starkey-digital/workbench, runs `claude plugin uninstall workbench@workbench` and `claude plugin marketplace remove workbench` (`claude_accounts::claude_binary`, `CLAUDE_CONFIG_DIR` for non-default accounts). Workbench never edits those settings or registry files itself.
- `pty.rs` — `pty::spawn(&pair, cmd)` starts every terminal shell (server terminals, macOS native terminals) without forking: Linux `posix_spawn` with `POSIX_SPAWN_SETSID` + opening the slave in the file actions (glibc's setsid runs first, so that open makes it the ctty); macOS spawns `pty_exec.c` (built by `build.rs`, embedded, written to `~/Library/Caches/workbench/workbench-pty-exec-<hash>`) which calls TIOCSCTTY and execs the shell, because XNU runs file actions in the parent's context and never grants a ctty there (bash reopens its tty and gets one anyway, zsh doesn't and loses job control). Windows keeps portable-pty's ConPTY spawn. Old glibc (no `addchdir_np`/SETSID) or a shim that cannot be installed falls back to portable-pty (fork) with a warning. A bare program name is looked up on the command's PATH only, never in the cwd

### Server crate (`apps/server/src/`)

### Frontend IPC & transport abstraction

Control-plane stores call `invoke`/`listen` imported from **`$lib/transport`** (not `@tauri-apps/api` directly). That module holds the active `ControlPlaneTransport` (`@workbench/transport`): `createTauriTransport()` (default, local IPC) or `createHttpTransport()` (remote server). The shims keep Tauri-compatible signatures so call sites are unchanged. xterm panes talk to the loopback server's terminal WS; **native (macOS) terminal IO**, native dialogs, window/menu, and hook/terminal events stay on **direct `@tauri-apps/api`** — desktop-local, never routed remotely. `transport().capabilities.terminalIO` feature-detects local vs remote. `HttpTransport` and `agentClient` requests run under `withTimeout` (`@workbench/transport`; a timer + `AbortController`, since macOS 10.15 WebKit lacks `AbortSignal.timeout`; 10s default; routes that wait server-side get more: chat starts 90s, worktree add/remove 120s, usage 60s), so a stalled server can't pile requests up in the WebView's connection pool. `HttpTransport.subscribe` still opens a `/events` WebSocket the server doesn't serve (a stub, backing off to 30s); the server's one event stream is the SSE `GET /events/home`, which only the phone uses (the desktop's `AdoptionPoller` still polls).

`@workbench/transport` is the only place `@tauri-apps/api` may be imported among shared packages (in `tauri.ts`, an optional peer dep). Events from Rust→frontend: `terminal:data`, `terminal:activity`, `terminal:exit` (native terminals); `project:refresh-requested`, `codex:notify`, `agent:attention`.

### Frontend structure

**Stores** (`src/lib/stores/`): Context-based (`createContext` pairs in `context.ts`). Classes with `$state` runes. App.svelte creates instances and sets context sequentially; children use `getXxxStore()` getters. Stores created later in the sequence can call `getXxxStore()` in field initializers instead of receiving constructor params — avoids argument drilling.

**Features** (`src/lib/features/`):

- `projects/` — Sidebar, project dialog, project manager
- `workspaces/` — Workspace tabs, landing page
- `terminal/` — Terminal tabs, grid layout, terminal pane (xterm.js), cross-device adoption
- `claude/` — Session resume menu
- `chat/` — Chat view of a Claude or Codex pane (`SessionChat` hosting `@workbench/chat-ui`; `agent-api.ts` adds the hook socket to starts, `chat-platform.ts` is the Tauri `ChatPlatform`; Terminal | Chat toggle in `TerminalGrid`, persisted as `TerminalPaneState.view`; `pane-handoff.ts` (`codexTerminalAfterChat`) is Codex-only). ### Terminal persistence

All TerminalGrids render simultaneously, hidden via `class:hidden` when inactive (keeps xterm.js mounted and PTY alive). The `active` prop triggers `fitAddon.fit()` via `$effect` + `requestAnimationFrame` (ResizeObserver doesn't fire on `display:none`).

**PTY IO never blocks a shared thread.** A PTY master write blocks once the shell's input queue (~1 KB on macOS) is full, e.g. a paste while a foreground job isn't reading. So each terminal writes on its own thread: server terminals (`terminal.rs` `spawn_writer`) take input from a bounded queue (`INPUT_QUEUE`), and the attach loop holds a chunk the queue can't take and stops reading that socket until there's room (output, takeover and revoke still flow; held input is dropped after a takeover); `type_keys` and the startup command queue too. Native terminals (`native_terminal.rs`) queue keystrokes from SwiftTerm's main-thread `input_callback` and `write_native_terminal` on an unbounded queue (no producer may block), never call `swift_term_resize` (a `DispatchQueue.main.sync`) while holding the session lock, and hand output to SwiftTerm and `terminal:data` at most once per 33 ms frame (`pump_output`; a UTF-8 character cut at a frame's end waits for the next). Create/resize/kill run on `crate::blocking`; resizes record the requested frame first and each applies the latest, so pool reordering can't leave a stale size. `swift_term_destroy` is synchronous, so `destroy_view` (kill and shell exit) frees the callback context only once no callback can run. Every server WS send (terminal and chat) goes through `state::ws_send`/`ws_close`: 30s plus 1s per 16 KB of frame, then the socket is dropped, so a phone that stopped reading can't pin its task or hold up a revoke/takeover. `apps/server/tests/terminal_input.rs` pastes 512 KB into a sleeping shell on a one-worker server runtime and checks `/health` and the bytes.

**Cross-device terminals.** The loopback server's terminal list includes terminals opened from other devices (shared managers). `AdoptionPoller` (`features/terminal/server-terminals.ts`, started in `App.svelte` only after `workspaceStore.load()`; one `adoptionRound` per source, terminals then chats) polls every 5s while visible + on window focus and calls `WorkspaceStore.adoptServerTerminal`, which adds a background tab to the matching xterm workspace (worktree, then main; never native, never creates workspaces) with `serverTerminalIds` preset. `terminal-connection.ts` **claims** every id this webview created/attached/killed and `listServerTerminals` returns null while a create is in flight — otherwise a pane's own PTY (listed before its id reaches the store) or a just-killed one would be adopted as a duplicate. The server allows ONE attacher: a new attach sends `{"t":"takeover"}` to the old socket. Adopted panes (`PaneAdoption`) are excluded from the persisted snapshot (`withoutPanes` — their loopback PTYs die with the app, so they'd reopen as phantom shells; after a reload they're simply re-adopted), and closing one ends it like an own pane (a session is the same whichever device started it; only who has control differs): `DELETE`, and its id is released so it isn't re-adopted. They mount **detached** (`connectDetached`) and a taken-over pane stays detached, both showing "Take control" (`TerminalConnection.takeControl`) — never auto-reattach, or two devices ping-pong. Mobile-created PTYs have no `WORKBENCH_PANE_ID`/hook socket, so hook-based activity tracking only covers desktop-created panes. Panes send a readable `name` (`paneDisplayName`) alongside `paneId`.

**Cross-device chats.** The same poller (rounds run in parallel via `allSettled`) lists `GET /agent/claude` (`listAgents`); `WorkspaceStore.adoptableServerChats` first moves panes still on an id a `/clear` replaced to the new one (`AgentSummary.previousIds` — the server keeps old ids as aliases; mobile sends no `paneId`, so this is the only reliable link), then filters (`adoptableChats`): exited sessions, ids any pane shows (session or `paneId`), ids a live chat in `chat-registry` holds (`isChatClaimed`), and closed-here tombstones. A tombstone lives only while the server still lists the session (still stopping, or the other device keeps it), so a session that ended and was continued elsewhere is adopted again. `adoptServerChat` adds a background `view: 'chat'` Claude tab (worktree then main workspace, same rules); with none open it opens one in the background for the chat's registered project (xterm, unselected, branch from `GitStore`), left out of the snapshot while it holds only adopted panes and closed when its last tab goes (`PaneAdoption.markCreated`/`isAbandoned`). Adopted tab labels follow the chat's title each round (`PaneAdoption.relabels`). Its `SessionChat` starts with **`attachOnly`**: the server returns the running session or 404 ("ended on the other device"; `ended: true` in the body when someone ended it, vs it exited) and never spawns, so no sandbox/cwd check applies. **An End anywhere closes the chat everywhere**: closing a pane on any device ends its chat, whoever started it: `DELETE /remote/terminals/:id` Ends the chat its terminal hosts before killing it (`AgentManager::end_terminal`; every caller is a deliberate close), and the desktop also stops own AI panes by `paneId` (Codex chats have no terminal) and adopted chats by session id (a phone sends no `paneId`); a restart is no End, and attached clients get `exit` with `ended` (an attach-only start, the 404 with `ended`), which fires `AgentChat.onEnded`: the desktop's `closeEndedChat` only detaches (nothing is stopped again), the phone leaves the screen unless the End was its own. An adopted chat is joined at adoption (`attachAdoptedChat`), not when first shown, so it hears an End; a crash or a session that merely drops off the list keeps its exited UI. Adoption bookkeeping (one adopted-pane set for terminals and chats, tombstones, tab builders, re-keys) lives in `PaneAdoption` (`features/terminal/pane-adoption.ts`). The tab-level Restart (`restartAISession`) on an adopted chat re-attaches (`reopenChat`) instead of stopping it. **Takeover paths** (the pane stops being adopted, is persisted, and closing it stops the process): reopening an attach-only chat once it has ended or failed (the in-chat Restart / Try again; `AgentChat.onTakeOver` → `takeOverPane`) starts it here; Claude view switches retain the adopted session and its backing terminal (mounted detached until Take control); `/resume` stops the current process (`stopAgent`) first.

### Claude CLI integration

- Every Claude pane (xterm or native) picks its session UUID up front; its terminal create sends `claudeSession` (`claudeSessionLaunch(pane)` → `{id, prompt?}`, `prompt` = an agent action's, persisted as `claudePrompt`) and Rust builds the command (`claude_launch`; the server picks `--resume` when `agent::claude_history_exists`, else `--session-id`). Codex panes use `codex:notify` + quiescence. JSONL discovery is on-demand for resume/history and label enrichment.
- **Notifications ("needs you") are event-driven:** Claude's plugin `/mod/out` and Codex's app-server stream update `AgentSession`, which publishes state transitions synchronously to `AgentManager.attention` (`attention_feed.rs`, one shared cursor-based history; no session polling). The desktop's `ServerControl::watch_attention` subscribes and emits `agent:attention`; Android's native background service consumes the exact same events through authenticated `GET /agent/attention?cursor=…` long polling, replays retained events after a disconnect, and clears resolved approvals. Token rotation/listener stop revokes outstanding requests. New subscriptions and server epochs seed silently; the latest 512 events are retained. Codex **terminal** `notify` payloads use `type: "agent-turn-complete"`; the hook bridge mirrors those completions into the same feed, while `codex:notify` only updates desktop labels/activity to avoid a second alert. A live Codex app-server session's notify is ignored because its stream already published the completion. Terminal notification links attach the existing server terminal and never start an app-server on the TUI's session file. `ClaudeSessionStore.onAttention` maps attention to a pane (`paneForAgent`: pane id, then session id, then terminal id) or notifies a session no pane shows by title ; `resolved` withdraws it (`remove_native_notification`, macOS only). A terminal-owned dialog (`/mod/ask` fell back) stays `waiting` with `inTerminal: true` until resolved; keep-alive turns do not publish completions.
- Quiescence (Codex panes only): per-pane debounce on terminal output (WS data, or native `terminal:data`/`terminal:activity`). After 1s of no output, pane marked as needing attention.
- Codex session ids come from the CLI; Claude's are picked by the frontend (above), and a pane follows its `claude` onto another session (`/resume` in the TUI). A chat pane's id comes only from its chat (`isChatPane`).
- **Multiple Claude accounts** (`workbench_core::claude_accounts`, StatusBar `ClaudeAccountSwitcher`): each extra account is a `CLAUDE_CONFIG_DIR` (verified on Claude Code 2.1.286: it alone isolates the login, `.claude.json`, settings, hooks and `projects/`). Both switchers change the host's `activeClaudeAccount` through one core fn, `claude_accounts::set_active` (only that field is rewritten): the desktop's via the Tauri `set_active_claude_account`, the phone's via `PUT /settings/active-claude-account`; each bumps `Managers.settings` and `ServerControl::watch_settings` emits `settings:changed` so the desktop reloads. The snapshot carries `claudeAccountId`, and `AgentChat` follows it (later starts use it; `onAccount` → the desktop pane's `claudeAccountId`, the phone's `ChatRef`); `syncFromAgents` also moves a pane onto its summary's account, so a switch from another device sticks. ### Git worktree support

- Workspaces have optional `worktreePath` and `branch`. Main workspaces resolve branch from `gitStore.branchByProject` at read time (no sync needed). Worktree workspaces get `branch` set at creation time. When `worktreePath` is set, terminals and Claude sessions use it as cwd.
- `effectivePath(ws)` returns `ws.worktreePath ?? ws.projectPath` — use everywhere a workspace cwd is needed.
- Multiple workspaces share the same `projectPath` (one main + N worktrees). `getByProjectPath()` returns only main workspace.
- Sidebar nests worktrees under parent project. Git state lives in `GitStore` (`branchByProject`, `worktreesByProject`), accessed via context.
- `closeAllForProject()` closes main + all worktree workspaces.
- Worktree location strategy (workbench setting): `"sibling"` creates `<parent>/<repo>-<branch>`, `"inside"` creates `<repo>/.worktrees/<branch>` (auto-adds to `.gitignore`).
- `WorkbenchSettingsStore` manages `~/.workbench/settings.json` — single-scope store (vs multi-scope `ClaudeSettingsStore`).

### GitHub CI integration

- `GitHubStore` polls project status (PRs, workflow runs, PR checks) on 90s cycle, 15s fast-poll when pending.
- Polling is scoped to projects with active Claude/Codex sessions (`activeSessionsByProject`), not all open workspaces.
- `get_project_status()` batches all data in one IPC call: PRs, workflow runs grouped by branch, and pre-fetched PR checks for open PRs.
- `gh run list` returns `databaseId` (not `id`) — use `#[serde(alias = "databaseId")]` for deserialization.
- `gh repo list --json` valid fields include `name,nameWithOwner,description,isPrivate,isFork,url,sshUrl` — `httpCloneUrl` does **not** exist and causes `gh` to exit with an error. The `url` (web URL) also works as an HTTP clone URL.
- `gh pr checks` returns empty string `""` for `completedAt` on pending checks — validate parsed dates before computing durations.

- **Mobile:** same project, release `workbench-mobile@<version>`. Webview: `apps/mobile/src/sentry.ts` (`@sentry/svelte`, prod-gated like desktop). Native: `sentry-android-core` in the `session-notifications` plugin (`Telemetry.kt`; auto-init off, started from the plugin's `load` in non-debuggable builds only), covering Kotlin crashes/ANRs plus the notification service's diagnostics — once-per-process warnings for a poll stall (>60s between polls, with Doze/battery-optimization state), alerts blocked in Android settings, non-200 polls, unexpected exceptions; breadcrumbs for poll failures and alerts posted/skipped. Never record tokens, URLs or session titles. No Rust Sentry on mobile (thin shell).
- **Source maps:** release builds upload the frontend's hidden source maps through `@sentry/vite-plugin` (`scripts/sentry-vite.ts`, used by both apps' `vite.config.ts`), only when `CI` and `SENTRY_AUTH_TOKEN` (org secret) are both set (each desktop OS uploads its own bundle, Android only for tagged releases), under the same release name `Sentry.init` reports, then delete the `.map` files so they never ship. No token (local, PRs): no maps, nothing uploaded. A failed upload logs and the build carries on.
- **Close Sentry issues as they're fixed.** A PR that fixes a Sentry issue names it in its body on a line of its own starting `Fixes WORKBENCH-X` (one line per issue; `Closes`/`Resolves` work too; mid-sentence mentions don't count); Kodiak's squash keeps the body in the commit, and the release workflow's `publish` job resolves every issue named since the previous tag once the release is out, as resolved in that release (`workbench@<version>`), so only an event from that release or later reopens it as a regression. Before opening a fix PR, look the error up in Sentry (`sentry-admin issues starkey-digital -p workbench`) and name the issue. Something fixed outside a release (stale, not ours, already gone): resolve or ignore it by hand with `sentry-admin resolve|ignore starkey-digital WORKBENCH-X`, so the open list only holds live problems.
- **Prod/test gating (backend):** the Sentry client is a no-op when `cfg!(debug_assertions) || cfg!(test)` — so `cargo test`, `cargo test --release`, and `tauri dev` never report upstream.
- **Backend logging:** `observability::init` also installs a global `log` logger (`env_logger` → stderr and `<config dir>/logs/workbench.log`, rotated once past 5 MB at startup; respects `RUST_LOG`, default `info`) wrapped by Sentry. The server's `tracing` events reach it through tracing's `log` feature, including `watchdog.rs`'s: an error when the server runtime's async workers or blocking pool leave a task waiting 5s, or open files pass 80% of the limit, and a warning per request unanswered after 45s. The desktop's `run()` and the standalone `main` raise the soft open-file limit at start (`watchdog::raise_fd_limit`; spawned shells inherit it, see its doc): launchd gives a GUI app 256, and at that ceiling `accept` fails and the API stops answering (`apps/server/tests/fd_limit.rs`). Whoever builds the server's runtime calls `watchdog::start`. The server runs its own accept loop (`accept.rs`) so each accepted socket gets TCP keepalive, and terminal/chat WebSockets are pinged every 30s and dropped after two missed pongs (`state::Heartbeat`; `WORKBENCH_WS_PING_MS` for tests), so a vanished phone's sockets are freed (`tests/dead_peer.rs`). In release: `log::error!` → Sentry **event**, `log::warn!`/`log::info!` → **breadcrumb** (shown on the next event). Use `log::warn!`/`log::error!` for backend diagnostics, **not** `eprintln!`. Stderr output works in all builds; Sentry forwarding only in release.

### Svelte 5 reactivity

**`$derived` is king** — use for all computed state. `$derived.by` for complex expressions. Writable `$derived` (Svelte 5.25+) for computed values that can be temporarily overridden.

**`$effect` is an escape hatch** — only for external side effects like network requests, DOM manipulation, and analytics. Per the Svelte docs: "In general, `$effect` is best considered something of an escape hatch — useful for things like analytics and direct DOM manipulation — rather than a tool you should use frequently. In particular, avoid using it to synchronise state."

**Never use `$effect` to sync state.** Don't read reactive values in an effect and write them to other reactive state. Instead, use `$derived` or `$derived.by`. If you need a computed value that can be reassigned (optimistic UI), use writable `$derived` instead of an effect.

**`runed` is available** — for unavoidable side effects prefer `watch(() => dep, (v) => {…})` (tracked dependency getter, untracked callback) over `$effect`. Don't refactor pre-existing `$effect`s unless asked.

**Cross-component reactive state:** Derive in the store (where the data lives), not via effects in components. If multiple components need the same derived value, put the `$derived` on the store class, not in each component.

**Cross-store derived state:** Put the `$derived` on the store that owns the concept (e.g., `activeBranches` on `GitHubStore`), not as an `$effect` in a component that reads one store and writes to another.

## Gotchas

### Monorepo

- **Pure logic goes in `workbench-core`, not desktop.** When adding shared logic (git, config, sessions, settings), put it in `crates/workbench-core` and (if it needs a Tauri command) add a thin wrapper in `apps/desktop/src-tauri/src/commands.rs`. Never add `tauri` to core or server; re-export new core modules at the desktop crate root in `lib.rs`.
- **Adding a server endpoint** = add the route in `apps/server/src/routes.rs` calling a `workbench_core` fn, reuse a `types.rs` struct for the body/response (camelCase so it matches frontend), and (if the desktop/mobile client should call it) add the command name to `ControlPlaneCommands` + the route mapping in `packages/transport/src/http.ts`. Exception: the chat-session routes (`/agent/claude…`) have no Tauri IPC twin and pair with a WebSocket, so both apps reach them through `agentClient` in `@workbench/chat-ui`; add new agent routes there.
- **Control-plane stores import `invoke`/`listen` from `$lib/transport`**, not `@tauri-apps/api`. Native terminal IO / dialogs / window APIs stay on direct `@tauri-apps/api`; xterm IO goes over the server's terminal WS. Never route terminal IO through the transport.
- `@tauri-apps/api` must not be imported in `packages/*` except `transport/src/tauri.ts` (optional peer dep) — keeps shared packages buildable by the mobile app.
- bun workspaces nest `@workbench/*` symlinks under the **consumer's** `node_modules` (e.g. `apps/desktop/node_modules/@workbench/transport`), not hoisted to root. A new workspace dep needs declaring in the consumer's `package.json` (`"workspace:*"`) + `bun install`.
- `TauriTransport` uses **static** imports of `@tauri-apps/api` (not dynamic) so call timing/arg-shape match what stores/tests expect; it omits the args object when undefined.
- UI primitives import from `@workbench/ui/<component>` and `cn` from `@workbench/ui` (NOT `$lib/components/ui` / `$lib/utils` anymore). `components.json` (shadcn CLI) aliases still say `$lib/...`; if you `shadcn add` a component it lands in the app — move it into `packages/ui/src/ui/` and fix its `$lib/utils` import to `../../utils`.
- `WORKBENCH_CLAUDE_BIN` (default `claude`) names the CLI that chat and terminal launches run (`claude_launch`) — set it to a fake script in tests, or to point at an alternative CLI.
- **Left sidebar is instance-aware** (`$features/instances/`): `InstancesStore` holds the implicit local instance ("This Mac") plus persisted remote servers (localStorage), each remote owning a `ControlPlaneStore` (HttpTransport) + health-polled status. `InstanceSwitcher` (dropdown in the sidebar header) sets `activeId`; `App.svelte` renders the rich terminal-coupled `ProjectSidebar` when local, else `RemoteInstanceSidebar` (sidebar chrome + shared `ControlPlaneSidebar`). `ConnectInstanceDialog` adds a server (name/URL/token + `/health` test). So: control-plane features that should work on remote instances belong in the shared `ControlPlaneSidebar`, not `ProjectSidebar`.
- **Server-mode token UX** lives in `components/settings/SettingsServerMode.svelte`: first enable calls `WorkbenchSettingsStore.ensureServerToken()` (Rust `rotate_server_token`), the token is shown masked with reveal/copy, and Regenerate (`ConfirmDialog`) calls `rotate_server_token` so old clients are cut off. The mobile app refuses to connect without a token and verifies it on `/remote/terminals` (`/health` is unauthenticated).
- **QR pairing** (`workbench://pair?v=1&url=…&token=…`, only via `buildPairingUri`/`parsePairingUri` in `@workbench/transport`) and the **Android in-app updater** (`apk-updater` plugin) have many platform traps (custom-scheme parsing, scanner cancel never settling, background activity starts). **Read `docs/MOBILE.md` before changing either.**
- `ProjectConfig.startupCommand` / `tasks` are legacy: no UI edits or runs them (the Scripts tab replaced tasks), but Rust keeps them and `ProjectManagerStore.save` spreads the saved project so an edit doesn't drop them from `projects.json`.
- Adding a `WorkbenchSettings` field touches 5 places: Rust `crates/workbench-core/src/types.rs` (field + `default_*` fn + `Default` impl), TS `apps/desktop/src/types/workbench.ts` interface, store `workbench-settings.svelte.ts` (field decl + `load()` + `toSettings()`), and `workbench-settings.test.svelte.ts` — two exact `toHaveBeenCalledWith('save_workbench_settings', …)` assertions list every field, so both break until updated.
- **A desktop command that blocks (git, gh, file or process work) is `#[tauri::command] pub async fn` wrapping its body in `crate::blocking(move || …).await`**, never `#[tauri::command(async)]` on a sync fn: Tauri runs those on its runtime's workers, so a burst held up every other command and event. The embedded server listeners run on their own runtime (`server_control::server_runtime`), so nothing a command does can starve the phone's or the panes' connections.
- Rust modules use `anyhow::Result` internally. `commands.rs` converts to `Result<_, String>` for Tauri IPC via `.map_err(|e| e.to_string())`.
- Config/settings writes use `paths::atomic_write()` (temp file + rename) to prevent corruption.
- **`window.confirm` is broken under Tauri and cannot be fixed with a capability.** `tauri-plugin-dialog` injects an init script into every webview that replaces `window.confirm` with an async `invoke('plugin:dialog|confirm')` — but the plugin only registers `open`/`save`/`message`, so that command does not exist and no permission grants it (`dialog:allow-confirm` is a deprecated alias for `allow-message`). Any bare `confirm()` therefore rejects with "not allowed by ACL", and its return value is a Promise (always truthy) even when it doesn't. Never call `confirm()`; use `ConfirmDialog`/`ConfirmAction`. This is why `TerminalPane` must pass an explicit `linkHandler` to `new Terminal()` — xterm core's OscLinkProvider falls back to `confirm()` + `window.open()` for OSC 8 hyperlinks, which silently swallowed every such link click.
- **Never spawn a child process with `Command::new` — use `workbench_core::shell::command()`.** Release builds link `windows_subsystem = "windows"`, so the app owns no console and Windows pops a visible blank console window for every console child (`git`, `gh`, `taskkill`, …). `shell::command` sets `CREATE_NO_WINDOW`. Same module owns `default_shell()` / `login_args()` / `inherited_env()` — the per-platform shell setup shared by the desktop's native terminals and the server's `TerminalManager` (`-l` is Unix-only; passing it to `cmd.exe`/`powershell.exe` fails the spawn). **No `pre_exec`, ever, and no `fork`:** std forks instead of `posix_spawn` when a command has a `pre_exec` (or uid/gid/groups/chroot, or a bare program with PATH changed — see `shell::tool`), and a fork in this many-threaded app holds macOS's allocator locks long enough to freeze every thread, embedded servers included. So never call portable-pty's `slave.spawn_command` (its `pre_exec` setsids) — use `workbench_core::pty::spawn` — and never `open::that_detached` (it setsids in a `pre_exec`) outside Windows: links go through `shell::open_url` (`/usr/bin/open` / `xdg-open` in its own group via `posix_spawn`; http(s), mailto and tel only; Linux tries `xdg-open`, `gio open`, `gnome-open`, `kde-open`, `wslview`), from the frontend via the `open_url` command (`$lib/utils/open-url`). `tauri-plugin-shell` was removed for this; don't re-add it.
- Mutex locks use `.unwrap_or_else(|e| e.into_inner())` to recover from poisoning.
- `tauri.conf.json` must have `beforeDevCommand` set or `tauri dev` hangs waiting for Vite.
- `.prettierignore` (at root) excludes lockfiles, `.claude/`, build output, generated Tauri dirs and `*.rs`. `tailwindStylesheet` in `.prettierrc` points at `./apps/desktop/src/app.css`. eslint config reads `../../.gitignore`.
- Rust types use `#[serde(rename_all = "camelCase")]` to match frontend field names.
- Store constructors run at import time. Side effects like `listen()` are fine — Tauri event system is available immediately.
- `ConfirmDialog` delegates close behavior to the bound `ConfirmAction.open` — don't auto-close on confirm (allows async error display + retry).
- Svelte 5 `$state` with union types: use `$state<'a' | 'b'>('a')` not `let x: 'a' | 'b' = $state('a')` — the latter narrows to the initial value's literal type.
- `$derived` on class fields is lazy — the callback runs on first read, not at field initialization time. Safe to reference constructor params that are set after field initializers run.
- **Context init order in App.svelte is load-bearing.** Stores that call `getXxxStore()` in field initializers will crash at runtime (`missing_context`) if the dependency hasn't been `setXxxStore()`'d yet. `GitHubStore` depends on `WorkspaceStore`, `GitStore`, `ClaudeSessionStore`, `ProjectStore`. Always verify the full dependency graph before reordering.
- **Never call `getXxxStore()` from runtime methods** (async handlers, callbacks, non-init code paths). It uses `hasContext()` which only works during component initialisation → `lifecycle_outside_component` error. Instead, cache the store as a field initializer (`private settingsStore = getWorkbenchSettingsStore()`) and use `this.settingsStore` in methods.
- When making a sync store method async, grep for all callers in `*.test.svelte.ts` — tests that don't `await` the call silently pass without verifying behavior.
- When gating a code path (e.g., adding approval before session launch), trace **all** callers of the underlying method — sidebar context menus, landing pages, terminal tabs, etc. may bypass the new gate.
- Dialogs using `bind:open` let X/Escape/outside-click close without resolving pending promises. Use `onOpenChange` to intercept dismissal when the dialog controls async flow.
- Every frontend `invoke('command_name')` call needs three things: (1) the `async fn` in a `_commands.rs` file, (2) registration in `lib.rs`'s `invoke_handler`, and (3) matching `#[serde(rename_all = "camelCase")]` types. Missing any one silently fails at runtime.
- Per-project config (like `TrelloProjectConfig`) must be loaded at startup in `App.svelte`'s `onMount`, not only from settings UI. Otherwise features depending on that config (sidebar panels, merge automation) won't work until settings is opened.
- Dialog pre-fill from props: don't use `$state(prop)` (captures initial value only). Instead, apply prop values in the dialog's `onOpenChange` callback when `isOpen` is true.
- `ScrollArea` internal viewport uses `size-full` (`h-full`) — `max-h-N` on the root doesn't constrain it. Use a fixed `h-N` for scroll areas that must stay bounded.
