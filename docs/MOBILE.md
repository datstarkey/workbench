# Mobile app (Android)

## QR pairing

Payload is `workbench://pair?v=1&url=<http(s) base url>&token=<token>`, built/parsed only by `buildPairingUri` / `parsePairingUri` in `@workbench/transport` (`pairing.ts`; the outer URI is matched as the exact prefix `workbench://pair?` — never `new URL()`, which older Android WebView parses differently for custom schemes — and duplicated params, non-http(s) urls, credentials, paths, queries, fragments and weak tokens are rejected). Desktop: "Pair phone" in `SettingsServerMode` (enabled while the LAN server runs, re-checked with Rust) opens `ServerPairingDialog` — address picker from the `pairing_addresses` command, bound port from `server_status`, QR drawn as an inline `<svg><path>` from `uqr`'s `encode()` (`server-pairing.ts`; no `{@html}`), plain-HTTP warning for non-Tailscale addresses, derived from the store so a rotated token redraws. Mobile: `@tauri-apps/plugin-barcode-scanner` / `tauri-plugin-barcode-scanner` (mobile-only target dep, `init()` under `cfg(mobile)`), permission in `capabilities/barcode-scanner.json` scoped to `platforms: ["android", "iOS"]` — tauri-build validates unscoped capabilities against the plugins built for the current target, so putting it in `default.json` breaks desktop-target builds of the mobile crate. CAMERA comes from the plugin's library manifest via the generated (gitignored) gradle wiring. `PairingScan.scan` (`qr-scan.svelte.ts`; scanner + `onBackButtonPress` injected), driven by `MobileClient.scanAndConnect`, does permission → **windowed** QR scan → `parsePairingUri` → `connect()` with the scanned origin used verbatim (only hand-typed URLs get the default port). The plugin's full-screen scan has no way out and its `cancel()` never settles the pending promise (nor does `scan()` on a device without a camera), so the app renders `ScanOverlay` (Cancel button; `html.qr-scanning` makes the page transparent so the camera shows through) and `PairingScan.cancel` — also wired to the Android back button, registered only during a scan because any back-button listener suppresses default back navigation — ends the scan itself and bumps a generation counter so a late result is ignored.

## Saved machines

The phone keeps several paired servers (`SavedMachines` in `machines.svelte.ts`: `wb.machines` = `{ id, name, url, token }[]`, `wb.activeMachine`) and is connected to one at a time. Pairing (QR or typed) adds a machine, or updates the saved one with the same URL (token rotation) or the same token (the same server reached by LAN IP, Tailscale IP or MagicDNS; tokens are random per server), and makes it active. Pairing offers an optional host nickname before scanning or connecting. The name defaults to the URL host; every saved host has a pencil button to rename it from the connect screen or the home screen's machine switcher (the header pill), including offline hosts. Renaming updates the header and notification monitor without reconnecting; nicknames survive relaunches, token rotation and address changes. Blank pairing nicknames keep the existing saved name; forgetting a machine is two taps (× then Forget, inline, since `window.confirm` is broken under Tauri). The pre-machines `wb.serverUrl` / `wb.token` / `wb.claudeTerminals` migrate into the first machine once, and are deleted only after the new list reads back from storage. State that belongs to one server is keyed `<key>.<machine id>` and removed with the machine; the default chat/terminal view stays phone-wide.

Switching verifies the target first (`server-check.ts`: `/health` + a token check on `/remote/terminals`, each with an 8 s `AbortSignal.timeout`, so an asleep or off-Tailscale machine fails fast) and only then tears down the current connection (store, screens, lists). A failed switch keeps the current connection and shows a notice. Two counters keep machines apart: `attempt` (bumped per connect, by `disconnect` and by forgetting the machine being connected to) lets a newer pick supersede a connect still waiting, and `generation` (bumped when the connection goes) makes every server operation (`showAsTerminal`, `answer`, list refreshes, …) bail after an await, so nothing started on one machine lands on, or is sent to, the next. The saved list stays usable while a connect is in flight.

## In-app updater

`updater.ts` (pure: GitHub `releases/latest`, strictly newer plain semver, no drafts/prereleases, both `workbench-android-<v>.apk` and `.sha256` assets under `https://github.com/starkey-digital/workbench/releases/download/`, 403/429 → rate-limit error) → `AppUpdater` (`app-updater.svelte.ts`, deps injected; launch check is silent, manual check reports) → `UpdateBanner.svelte` (bottom row: available / downloading % / needs permission / error). Native side is the local plugin `apps/mobile/src-tauri/plugins/apk-updater` (workspace member, Android-only target dep, capability `capabilities/apk-updater.json` scoped to `android`): Kotlin `downloadAndInstall({ url, sha256Url, onProgress: Channel })` re-checks the URL prefix, follows redirects only to `release-assets`/`objects.githubusercontent.com`, returns `needs_permission` after opening `ACTION_MANAGE_UNKNOWN_APP_SOURCES` when `canRequestPackageInstalls()` is false, verifies SHA-256 (deletes on mismatch) into `cache/apk-updates/<sha256>.apk` (reused by retries; pruned when a newer one downloads, cleared by `clear_downloads` once a check finds the app current) and opens the installer via its own `ApkFileProvider` (a `FileProvider` subclass, so it can't collide with the app's provider in the merged manifest). The sha256 only guards corruption; authenticity is Android refusing an update signed by another key. Android 10+ silently drops background activity starts, so when the activity isn't `RESUMED` the plugin returns `ready_to_install` + sha256 and the banner offers "Install" (`install_downloaded` re-hashes the file, no re-download). Activity starts are try/caught (not `resolveActivity`, which needs `<queries>` on 11+) and reject readably on devices without the settings screen or installer (Android TV, some OEM/work profiles). Silent install is impossible for sideloaded apps.

## Chat and terminal

The home screen (`Home.svelte`) lists what needs you (unanswered approvals from `GET /agent`, answerable in place via the agent's message endpoint), what is running (chats from any device, plus server terminals), and projects to start in. New Claude sessions open in the phone's default view (Settings sheet, `wb.claudeView` in localStorage, chat unless set).

- Claude chat and terminal are two views of one interactive `claude` process. Chat → terminal selects the existing server PTY; terminal → chat uses `attachOnly: true` to join its plugin. Neither switch stops or starts a process. A terminal waiting on login/trust stays open with a notice when its plugin hasn't attached yet. Home lists a live Claude session once, hiding its backing terminal from the separate terminal rows.
- The server builds the `claude` command for `claudeSession` itself (permission mode from settings, and the sandbox-runtime wrapper when it is on, failing closed if its settings file is missing). The phone never types a Claude command, so it can't skip the sandbox. Chats carry `claudeAccountId` from `GET /agent/claude`, and resumes and terminals keep it.
- Terminal associations come from the server's chat `terminalId` and terminal `claudeSessionId`. The chat's `onTerminal` callback follows mode/rewind replacements. Sessions opened on another device offer the same view switch. Opening a listed session attaches only; an explicit Restart can restart an ended session.
- Codex chat runs `codex app-server` over JSON-RPC, rather than an interactive CLI in a PTY. Android currently offers Codex chat only. A saved Codex thread can also be resumed in the CLI, but that is a different process, so Codex has no chat/terminal view toggle.
- Android drops sockets while the screen is locked. The terminal re-attaches when the app is visible again; the chat calls `AgentChat.reconnect()` after more than 10 s hidden, and the home lists refresh on `visibilitychange`.

Both apps and both agents use `@workbench/chat-ui`'s composer, attachment intake, transcript, model picker and mode controls. The shared paperclip accepts images, PDFs and UTF-8 text/code files, with the same limits on either host. Claude reads uploads through its terminal plugin; Codex keeps native image input and reads uploaded files from private server-side paths with its tools (PDF extraction depends on tools available on that server). Uploads are removed when the session ends. New Codex chats on either device use the server's saved Workbench launch preset; unmatched settings inherit Codex's own config, and an explicit chat mode takes precedence.

## Conversation history and review

Expanded projects and worktrees offer **History** (Claude or Codex, searchable) and **Review changes** (branch, changed files, staged/working-tree diffs). The chat's three-dot menu offers the same actions, plus **Open on GitHub** when the project has a GitHub origin. `/resume` opens history locally. Review uses the authenticated `/projects/git-status` and `/projects/git-diff` routes; both restrict the checkout to registered projects/worktrees. Untracked previews are bounded, and symlinks are shown without reading their targets.

Settings offers the server's saved Claude accounts for new sessions; history can filter by account, and resumed chats retain their original account. Codex slash completions use the app-server's `skills/list`, refresh on `skills/changed`, and send an explicit skill input with the server-discovered path.

Composer drafts are separated by machine, agent, account and conversation. Text survives app restarts; image attachments survive navigation within the app but are not saved to localStorage. The draft follows a newly assigned Codex thread ID or Claude `/clear` ID. Android Back dismisses the top sheet, then closes chat/terminal to Home; Home retains Android's default Back action.

Claude and Codex usage pills show their percentages around the border. Tapping a plan limit shows the remaining time and reset date/time in the phone's timezone; a CLI reset with no usable timezone stays as its original text. The context pill shows its percentage, and tapping shows used/max tokens. Markdown links in both agents' chats use the native system URL handler, outside the chat webview.

## Android voice input

The microphone button in Claude and Codex chat opens Android's native speech input dialog. Recognized text is inserted at the draft's selection, with the rest of the draft and attachments kept; review or edit it and tap Send. Cancel leaves the draft alone. The device's speech recognition app owns microphone access and may need a network connection; Workbench receives only text. A missing recognizer or failed recognition shows an error in the composer. The local Android-only `speech-input` plugin uses `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` and Tauri's activity callback, with no audio recording or speech API keys in Workbench. Leaving the conversation discards late results.

## Android session notifications

Notifications are opt-in in the phone's Settings. The local `session-notifications` Tauri plugin runs an Android `remoteMessaging` foreground service whenever notifications are on and the phone is connected to a machine, whatever screen is open. Claude plugin updates and Codex app-server events publish attention directly to `AgentManager.attention`; desktop Codex terminal `notify` completions join the same feed. The desktop subscribes to that feed and the native phone service long-polls authenticated `GET /agent/attention?cursor=…`, which waits for an event instead of repeatedly fetching session state. Both consume the same approvals, resolutions and completed turns; resolving an approval on either device clears the phone alert. A bounded server history retains the latest 512 events for reconnect catch-up, with an epoch in the cursor so a restarted server seeds silently. A new connection seeds without replaying old alerts. Listener stop/token rotation revokes outstanding requests. The phone watches every session, including while locked or backgrounded, and skips system alerts while the app is visible. Switching machine restarts it for the new one; disconnecting or turning notifications off stops it. Opening or closing a chat doesn't touch the service. A Codex terminal alert opens its existing server terminal; a desktop-only native terminal stays on Home with a notice rather than starting another Codex.

An approval asked in the terminal's own dialog (no chat was open when Claude asked) stays in `waiting` with `inTerminal: true` until it's answered there, so it still alerts; Home labels it "answer in its terminal" and offers no Allow/Deny. Cache keep-alive turns stay silent. Tapping a notification opens the saved machine and conversation or terminal. Android shows an ongoing monitor notification with a Stop action; Android 13+ asks for notification permission. Starting the monitor also asks, once per launch, to skip battery optimisation: Doze cuts an optimised app's network even with a foreground service, so polls time out while the phone is locked. Whether the app is on screen is read from the process importance when an alert arrives, because Tauri never forwards `onPause` to plugins (its generated `TauriLifecycleObserver` is never registered). `addPluginListener` needs `register_listener`/`remove_listener` in the plugin's permissions, or tapping an alert can't open its conversation. Credentials live only in the running service, and the service does not restart automatically after force-stop or reboot. An authorization failure stops monitoring. `/clear` re-keys are followed through `previousIds`. Tests cover both agents, approvals, fast turns, cursor replay, duplicate suppression, replacement ownership, conversation ID changes, and stale configuration handling.

Release builds report to Sentry (`Telemetry.kt`): a stalled poll (the executor's clock stops while the phone sleeps), alerts blocked in Android settings, failing polls and crashes, with breadcrumbs of alerts posted or skipped. These are **local notifications delivered by the native service**, not Firebase/FCM push. Push delivery would need a separate device-registration and server-side delivery integration.
